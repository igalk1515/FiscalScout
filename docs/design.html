Pursuit take-home · System design

FiscalScout

A scraper that reads a public entity's web pages and ranks every link by how likely it is to lead to a budget, an annual financial report or a finance contact. It pulls out the contacts and files themselves, ranks cheaply first and with an LLM only when needed, stores every result with the page it came from, and serves the data through a small, well-shaped API that also shows a crawl live.

Igal Babushkin · As built · November 9, 2026 · github.com/igalk1515/FiscalScout

Summary

This page holds two designs. Design A is what the take-home builds: one process and one database, built in the order the brief cares about. Design B is the ambitious version at Pursuit's real scale: the same stages split into independent pools, two stores, and search by meaning inside the documents themselves. Design B is written up, not built.

Rank

Cheapest tier that can decide

Every link is scored for free, with weights learned from labeled links and keywords set per crawl. An LLM sees only the links that are still unclear, in batches.

Extract

Contacts and files are results

A finance contact comes out as a name, title, email and phone, checked against the page text. A file comes out with its document type and fiscal year.

Crawl

Focused, not exhaustive

The crawler always fetches the most promising unseen URL next, so a page budget lands on the finance pages instead of the events calendar.

Store

Provenance on every record

Each link keeps every page it was found on, with anchor text, section heading and nearby text. Unique keys and indexes keep writes idempotent and reads fast as volume grows.

Serve

A small, well-shaped API

Start a crawl, filter and page through links and contacts, and read the OpenAPI docs generated from the same schemas that validate requests.

Watch

Every crawl is visible live

An event stream and a small watch page show the page being fetched now, counters, skipped pages with the reason, and the best results so far.

What the brief asks

The design starts from the brief, in the order the brief gives weight to. Two lines set that order.

Objective

"Build a web scraper that identifies high-value links on a web page, focusing on extracting relevant contacts and specific files (like "ACFR," "Budget," or related terms). The scraper can/should use an ML model, LLM, or another intelligent approach to prioritize relevant links. Additionally, provide an API to access the scraped data."

Important notes

"Beyond achieving the Objective, there are no strict requirements … A lot of people might not finish it but prioritizing what's important is a skill."

What this changes in the design

  • One hub page per entity. Each site has one finance page that lists most of the targets, two to four clicks from home. Finding the hub is most of the work.
  • Files live on other hosts. Every site keeps its files somewhere else: a CDN, a school-site file host, ClearGov or SharePoint. The crawl scope has to include file hosts linked from the entity's own pages.
  • The heading carries the meaning. Anchors often say only "Fiscal Year 2025". The heading above the link says what the document is.
  • The title varies. Three of the four sites say Chief Financial Officer. Only Bozeman says Finance Director.
  • Sites contain mistakes. A draft is linked as the report, and a 2020 link opens the 2025 file. The crawler should read the year inside the document, not trust the anchor.

Added while building, because a real crawl or a re-read of the brief showed the need:

  • A keyword editor and re-ranking. Keywords could first be set only in a JSON body. The start page and the results page now edit them, and a finished crawl is ranked again from its saved pages, without fetching.
  • A results page with search over documents and contacts.
  • Stopping a crawl, from the API or a Stop button on the watch page.
  • A discount for documents on another government's site. ASU's finance site links the State of Arizona's budget summaries, which ranked above ASU's own budget.
  • Two switches per crawl, both on by default: respect robots.txt, and use the LLM. With the LLM off, a crawl runs on rules alone.
  • A browser User-Agent by default, set with HTTP_USER_AGENT, and one retry of a 403 with Node's standard HTTP client.

Hard problems

The six questions any crawler design has to answer, with the answer in Design A (A) and in Design B (B). Each card links to the detail.

Loops and traps

A
Seen set of normalized URL hashes, canonical links, content hashes, at most five redirects with a cycle check, depth 3, 500 pages per host, calendar and repeating-path guards.
B
Same rules. The seen set moves to a Bloom filter in Redis.
Trap guards

The site's rules

A
robots.txt per host (Disallow, Crawl-delay), meta robots and X-Robots-Tag nofollow, on by default and switchable per crawl. One request at a time per site, at least a second apart. A browser User-Agent by default, configurable, and one retry of a 403 with Node's standard HTTP client. Retry-After on 429 and 503. A site that keeps refusing is reported as blocked.
B
Same rules, enforced by the worker that owns the host's partition.
Politeness

Sites built with JavaScript

A
Plain HTML first, then the sitemap. A page whose HTML looks empty is flagged needs_browser and reported. With the render tier on (off by default), Playwright opens flagged pages on the entity's own site, at most 20 per crawl.
B
A separate browser worker pool, so slow renders never hold up plain fetches.
Fetching

Queues and workers

A
The frontier queue is a Postgres table, so a stopped crawl resumes where it left off. One process runs a few async workers (3 by default) that claim the best URL whose site is free with SKIP LOCKED, so more processes need no rewrite.
B
Kafka or SQS partitioned by host, with separate pools for fetch, render, parse and rank, and OCR.
Queues and workers

Scanned PDFs

A
PDFs are ranked by their link, not their content. Reading the text layer of vague PDF links was left for the last step and not built, so scans are not detected yet.
B
OCR workers process flagged files that already score high, then chunk and index them.
Vague document links

Where the LLM runs

A
Never on whole pages or whole sites. Only on short link records (anchor, URL, heading, about 200 characters of context) that are still unsure after the rules, 50 per call, and on the small text block around an email to read the name and title.
B
Same, and a small classifier trained on the LLM's labels takes most of that load.
Link ranking

Architecture

Design A runs on one machine: one Node process runs the API and the crawler, next to one Postgres. The diagram uses the same grid as the Design B diagram, so the two can be compared box by box. Dashed boxes are later steps or Design B. Fetching and extraction are separate steps with the raw page saved in between, so pages can be re-ranked and tested without crawling again. The blue loop is what makes it a focused crawler.

Politeness

  • Fetch and cache robots.txt per host for 24 hours. Honor Disallow and Crawl-delay. Per RFC 9309, a 4xx for robots.txt means everything is allowed, and a 5xx or no answer means nothing is.
  • Each crawl has a Respect robots.txt switch, on by default. It covers robots.txt rules and crawl delays, redirect targets, browser requests, and page and link nofollow. Pacing, scope and page limits apply either way.
  • One request at a time per site, at least one second apart, longer when the site answers slowly. A site is a registrable domain: on the first real crawl, three asu.edu subdomains fetched in parallel shared one rate limit and answered 429. A 429 or 503 doubles a per-site backoff, up to a minute; success halves it.
  • Send the configured User-Agent: a desktop Chrome header by default, replaced with HTTP_USER_AGENT. HTTP fetches, robots.txt and the browser all use it, and robots.txt groups are matched on its first product token (Mozilla by default).
  • On a 403, retry once with Node's standard User-Agent, at least a second later, and show it as page.retrying in the live feed. When that client succeeds, the runner keeps using it for that origin. With robots.txt on, the retry also has to be allowed for the standard client.
  • Honor <meta name="robots" content="nofollow"> and the X-Robots-Tag header. Links on those pages are not followed.
  • On 429 or 503, wait for Retry-After. After repeated 403 or 5xx responses, pause the host and mark the crawl as blocked.

URL normalization and dedupe

Every URL is normalized before it is hashed into the seen set: lowercase scheme and host, default port removed, fragment removed, tracking parameters (utm_*, fbclid, gclid) and session IDs stripped, query parameters sorted, relative paths resolved. After a redirect, the final URL is stored too. When a page declares a rel="canonical" URL on the same host, that URL replaces it. A SHA-256 of the response body catches the same page served under different URLs.

Crawl scope

The crawler never wanders the open web. It stays on the entity's own site.

  • In scope: the seed's registrable domain and all its subdomains. A crawl that starts at asu.edu covers cfo.asu.edu.
  • A link to another domain is stored and ranked, but not crawled. A budget PDF on a CDN or a school file host becomes a result; the host itself is not explored, and social networks never are.
  • One exception: when an in-scope link redirects to another host, as Boerne's does to boerneisd.smartsiteshost.com, that host joins the scope of this crawl only.
  • Limits: depth 3 and a page budget per crawl. Low-scoring links wait at the back of the queue and are reached only if budget is left.
  • Visible: every URL left out is recorded with the reason, such as "out of scope", so the live view shows at once if a crawl starts to drift.

Queues and workers

The frontier queue is a table in Postgres, so a crawl survives a restart and the live view can show what is waiting. A few async workers in one process claim the best URL whose site is free, fetch it, extract and rank, and write the results. SKIP LOCKED lets any number of workers or processes share the queue without taking the same URL or hitting the same site at once. No host may use more than 30% of the page budget.

Claim the next URL

with next as (
  select f.crawl_id, f.url_hash
  from frontier f
  join hosts h on h.host = f.host
  join sites s on s.site = h.site      -- registrable domain
  where f.status = 'queued'
    and f.not_before      <= now()
    and s.next_allowed_at <= now()
  order by f.path_score desc
  limit 1
  for update of f, s skip locked
)
update frontier f
set status = 'fetching', attempts = attempts + 1
from next
where f.crawl_id = next.crawl_id and f.url_hash = next.url_hash
returning f.url, f.host;
-- same transaction: lease the site until the fetch is done
-- after the fetch: next_allowed_at = now() + max(delay, response time, backoff)
  • Retries only when a retry can help: timeouts, network errors, 5xx and 429. A 4xx such as 404 is final: the page is marked failed with its status and is not tried again. A 403 gets the one retry with Node's standard client first, and is final after it. A retry goes back to queued with not_before pushed out by exponential backoff with jitter, or by Retry-After when the server sends it. After three attempts it becomes failed.
  • Crash safety: a URL stuck in fetching for more than five minutes returns to the queue.
  • Host breaker: after five errors in a row the host is paused, and the crawl status says so.

Link ranking

Every link gets two scores, because a link can be valuable in two different ways.

Target score

Is this link a result?

A budget book, an ACFR, a finance contact page. The API sorts by this score.

"FY2026 Adopted Budget (PDF)" → target 0.95

Path score

Does this link lead to results?

A Departments menu or a Finance landing page. The frontier orders by this score.

"Departments" → target 0.05, path 0.60

Tier 1: rule signals

The score is a weighted sum, clipped to 0–1, stored with the list of signals that fired. These are the hand-set weights; the learned ranker below fits them on labeled links instead.

Learned weights · the default

The weights above were set by hand. The learned ranker reads the same evidence and fits the weights by logistic regression on labeled links. Each crawl chooses: ranker is learned (the default) or rules, and a re-rank can switch a finished crawl from its saved pages.

  • Features: 22 per link and keyword group. They cover where the keyword sits (link text, URL, heading, nearby text, host name) and whether the link text is just the document's name and year. They also cover the kind of link: a file, a page on the entity's own site, another platform, another government's site, a paper about the document, a menu. Keyword features scale with the group's weight, so the keyword editor still works.
  • Policy stays explicit: the year and draft discounts are applied after the model, as after the LLM. They are a ranking choice, not evidence of relevance.
  • Data: 22 public bodies, the four test sites and 18 others: cities, counties, school districts and universities. That gives 5,402 links with a keyword signal.
  • Labels: gpt-4.1-mini labeled every link against a strict definition of a target: the document itself, not its list page, a presentation or another government's report. All the labels cost $0.43. A hand check agreed on 58 of 60.
  • Training: Newton's method in about 100 lines, with no dependency. Every site counts the same, so one county's 476 department budget requests cannot set the weights for everyone.
  • Result, leave one site out: AUC 0.833 against 0.762 for the hand-set weights. Labeled targets among each site's ten best documents: 132 of 170 against 118. On the test sites, a model that never saw them finds 12 of 12 must-find targets, as the other rankers do, and gets ASU to 10 of 10 without the LLM.

Configurable keywords

Each crawl takes its own keyword set. Synonyms matter in public finance: the ACFR was called the CAFR until 2021, and the person you want might be titled Treasurer or Comptroller.

The same keywords can be edited without writing JSON. The start page has a keyword editor, with a card per group: kind, a weight slider, synonyms, and related titles for contacts. The LLM tier, and embeddings later

  • LLM: it never sees a whole page or a whole site. It sees short link records (anchor, URL, heading, about 200 characters of nearby text) for links the rules left between 0.2 and 0.7, in batches of about 50, with a strict JSON schema: type, target score, path score, a short reason. The code validates every answer and keeps the rules score if the call fails. The product never depends on the model behaving.
  • Cache: every LLM answer is stored under a hash of the model, the prompt version and the input. A rerun on the same pages pays nothing and gives the same result, and tests run offline on the stored answers.
  • No key, no LLM: without an API key the LLM tier is skipped. Unsure links keep their rules score, and contacts come from simple patterns such as "Name, Title". The whole system runs end to end without paid services.
  • After the LLM, the rules' multipliers still apply: older fiscal years, drafts, pages on the entity's own site (nearly always the list, not the document), and documents on another government's site. With the last one, ASU's top 10 is all its own documents, and the state's budget summaries come 11th and 12th. Built and checked against the real API: the LLM confirmed ASU's ACFRs that the rules left at 0.52-0.69, and gave every year 1.00 until the year multiplier was applied after it.
  • Spending cap: LLM_MAX_USD_PER_CRAWL (default $0.50). Past it, the crawl continues on rules alone. A crawl of the three reachable test sites cost a few cents with gpt-4o-mini.
  • Embeddings, later: cosine similarity between the link's anchor plus context and each target concept would catch paraphrases that no keyword list covers, and take load off the LLM. It is the first thing to add once the evaluation shows where the rules miss.

Vague document links · not built

Planned for the last step and not built; this is how it would work. A link that says only "View" or "Document 1234" gives the rules nothing to work with. For PDF links with a promising path score, the crawler downloads the file (under the size cap) and reads the text layer of the first two pages. The LLM then returns the document type and fiscal year. Most budget books and ACFRs are generated digitally and already have a text layer. A PDF with no text layer is a scan. It is flagged needs_ocr and keeps its link-level score. In Design B, OCR workers process flagged files that already score high.

Contacts and files

The brief asks for "relevant contacts and specific files", so both come out as results of their own, not only as links. The finance contact is a person: a name, a title, an email and a phone. A file is a document with a type and a year.

Contacts

  • Find: rules pick up every mailto: and tel: link, every email or phone number in the page text, and every place where a title from the keywords appears, such as Chief Financial Officer or Finance Director. Titles matter because some contacts have no email on the page: ASU lists its CFO by name and title only. This step is free and runs on every page.
  • Read: for each email or title found, the LLM gets only the small block of text around it and returns name, title, email and phone in a fixed schema. A field that is not there stays empty.
  • Verify: the code checks that every value the LLM returns appears in that block, character for character. A value that is not in the page is dropped, so the model cannot invent a contact.
  • Score: the title is matched against the crawl's keywords, so a Chief Financial Officer ranks above a receptionist on the same page. Contacts are unique per host and name, so the same person found on three pages is stored once.

Files

  • Document type (acfr, budget, single_audit, …) from the anchor, the heading above the link and the file name, using the keyword synonyms. The LLM decides when these disagree.
  • Fiscal year from patterns such as "FY2026", "2025-26", "Fiscal Year 2025" and "June 30, 2025", in the anchor first, then the file name, then the heading.
  • File type from the extension or the Content-Type of a HEAD request: PDF, Excel, or an HTML page such as the ClearGov budget viewer.
  • Draft when the name or anchor says draft or proposed. A draft ranks below the final for the same year.

Data model

The key split is between a link and its sightings. The same budget PDF can be linked from the Finance page, the Council page and a news post. It is stored once in links and three times in sightings, so there are no duplicates and every source is kept.

  • Scores belong to a crawl. Keywords are set per crawl, so the same link can matter for one keyword set and not for another. links holds the facts about a URL, and link_scores holds each crawl's scores. Because pages are saved, a new keyword set can be scored against saved pages without fetching again.
  • Idempotent writes: every table has a natural unique key (URL hash; crawl and link; crawl, host and name; link, page and crawl), so every write is an upsert. Analyzing a page twice, or retrying after a crash, never creates duplicates.
  • Batched writes: all links found on a page go in one statement, not one row at a time.
  • Indexes match the API's filters, and pagination uses keys, never OFFSET, so reads stay fast at millions of rows.
  • Raw bytes stay out of the database. Pages are gzip files on disk, keyed by URL hash.

The q parameter runs Postgres full-text search over each link's label and URL, which is enough for exact terms such as ACFR, FY2025 or a person's name. Search by meaning, with vectors merged with the keyword results, is a Design B step (see Search inside documents).

Evaluation

Ranking quality is measured, not eyeballed.

  • Must-find list (eval/must-find.json, written by hand before the crawler ran): for each site, the latest budget, the latest ACFR and the finance contact with the right title and email. A target counts as found when it is in the top 10 of its type. Recall on this list is the headline number: 12 of 12 across the four sites, with the LLM, with rules alone and with the learned ranker. Bozeman's finance director was the last one found: the staff directory lists her last name first, in a table.
  • Precision@10 for documents: how many of the ten best name a finance document in the link text, the URL or the heading above the link, and belong to the entity. A host listed as someone else's, such as the State of Arizona's budget office, never counts. With the LLM it is 10 of 10 at Ann Arbor, Boerne and ASU, and 9 of 10 at Bozeman. With rules alone, ASU drops to 7 of 10. The learned ranker matches the LLM without calling it.
  • Cost per tier: how many links the LLM decided, and what the run cost.
  • The same crawls, ranked twice: once with the LLM and once with rules alone, from the saved pages. Results are in eval/results.md and eval/results-rules-only.md.
  • A labeled set across 22 sites: 5,402 links labeled by an LLM and spot-checked by hand, scored leave-one-site-out. The learned weights beat the hand-set ones on 9 sites, lose on 2 and tie on 7. Details are in eval/results-learned.md.
  • Not built: a CI check that fails the build when precision drops.

Architecture

The same stages as the crawl loop, split into independent pools that scale on their own and talk through queues.

Search inside documents

Design A ranks links. Design B also reads what the documents say, because that is where buying signals live: a line item for body-worn cameras in a budget, or a council vote on a new permitting system.

  • Extract: the text layer for digital PDFs, OCR only for scans. Keep page numbers and table structure.
  • Chunk: split by section and table, about 500–800 tokens each. Every chunk keeps its document ID, page number and character offsets.
  • Index: each chunk goes into the search index with both keyword terms and a vector.
  • Search: hybrid retrieval merged with Reciprocal Rank Fusion, then a reranker on the top 50. Every hit links back to the exact page and offset it came from.
  • Why a second store here: millions of documents at a few hundred chunks each means hundreds of millions of chunks. Search over that needs to scale apart from the transactional database. Postgres keeps the records, and the index is a derived copy that can be rebuilt.

Where it gets hard

PressureAnswer
Per-host politeness limits big sites, not total throughputPartition the frontier by host hash and crawl thousands of hosts in parallel. Each host stays at its own pace.
Browser rendering is slow and expensiveA separate pool, used only for hosts flagged as script-built. Remember per host which fetch method worked.
LLM cost grows with linksThe cascade, caching by URL and content hash, and batching. Later, train a small classifier on the LLM's labels and keep the LLM for the hardest cases.
Refetching unchanged pagesConditional requests with ETag and If-Modified-Since. The scheduler visits pages that change often more frequently.
Seen set outgrows memoryA Bloom filter in Redis for the fast check, with the url_hash unique key in Postgres as the final word.
Failures at volumeRetries with exponential backoff and jitter, a dead-letter queue, and a per-host circuit breaker. Writes are idempotent upserts keyed by URL hash.

When to split storage

  • Start: one Postgres for relational data, full-text search and vectors. Raw bytes go to an object store keyed by content hash and never sit in the database.
  • Partition: split links and sightings by host hash once they pass about 100M rows.
  • Add a search index: when vectors pass about 100M or search load needs to scale on its own. Feed it from Postgres through an outbox or CDC, so it can always be rebuilt.

A lease renewed every 1.5 seconds lets another process take over only when the runner dies.A crawl whose runner dies waits 30 seconds before another process picks it up.
Scores stored per crawlKeywords are set per crawl, so a score only means something next to the keywords that produced it.More rows, and reading a link's score needs a join.
Contacts checked against the page textAn LLM can produce a plausible email that is not on the page. Only values found in the page are stored.Contacts shown as images or behind forms are missed.
Focused crawl with a page budgetPursuit needs a few high-value documents per entity, not a full copy of every site.Might miss a target buried under an unpromising path. The labeled set measures this.
Learned weights over hand-picked featuresThe hand-set weights were guesses. A linear model over the same evidence ranks better, stays explainable weight by weight, and runs free on every link.The labels come from an LLM and are noisy on borderline documents. The model cannot use evidence no feature describes.
Rules first, LLM lastCost, speed and repeatable results. Every decision records which tier made it.Rules need tuning per keyword set.
One database to startNo dual writes to keep in sync. Filters and full-text search run in one query.Search and storage scale together until the split trigger is reached.
Store every sightingCustomers trust a result they can trace. Debugging a bad score starts from its source.More rows. Cheap compared with the value.
A browser User-Agent by default, robots.txt switchable per crawlBozeman refused the crawler's own User-Agent and accepted a browser's. robots.txt stays on by default, and the header can be replaced with HTTP_USER_AGENT.The header does not name the crawler. Sites that also refuse Node's standard client, or show an interactive challenge, stay blocked.

Open questions

Answers to these would change the design, so they are worth asking before going further.

  • Is there already a list of entity websites to seed from, or known finance pages per entity?
  • Which targets matter most to customers: documents, contacts, or both equally?
  • How fresh does the data need to be? Days or weeks changes the recrawl budget a lot.
  • Are third-party agenda and document platforms in scope, or only the entity's own domain?
  • Bozeman refused the crawler's own User-Agent and accepted a browser's. Which User-Agent does Pursuit's crawling send today?
